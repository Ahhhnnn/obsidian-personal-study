## 一、为什么 Agent 评测是独立且复杂的工程问题

传统 LLM 评测是 Single-turn：一个 Prompt 进去，一个 Response 出来，判断对不对就结束。Agent 评测完全不同——Agent 不是"回答问题"，而是"在环境中执行任务"。一次评测涉及多轮工具调用、环境状态变更、以及最终结果的验证。

这意味着评测结构从一维变成了三维：

| 维度 | 传统评测 | Agent 评测 |
|------|---------|-----------|
| 执行过程 | 单次调用 | 多轮循环，轮数不固定 |
| 环境依赖 | 不需要 | 需要准备工具、沙箱、数据库等运行环境 |
| 评判对象 | 输出文本 | 执行记录 + 环境最终状态，缺一不可 |
| 可复现性 | 确定性高 | 同一任务多次运行结果可能不同 |

评测复杂度上升的根源在于：**你不能只看 Agent 说了什么，还要看它真正做了什么。**

## 二、评测架构全景图解读

下面这张图（来自 Anthropic）展示了 Agent 评测的核心组件和流程：

```
┌─────────────────────────────────────────────────────────────────┐
│                    Evaluation Suite（评测套件）                    │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐                      │
│  │  Task 1   │  │  Task 2   │  │  Task 3   │  ...               │
│  │  +Grader  │  │  +Grader  │  │  +Grader  │                    │
│  └──────────┘  └──────────┘  └──────────┘                      │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
                    ┌──────────────────┐
                    │  Agent Harness   │ ← 被测 Agent 的运行框架
                    │  (执行层)         │
                    └──────────────────┘
                              │
                    ┌─────────┴─────────┐
                    │                   │
                    ▼                   ▼
            ┌──────────────┐   ┌──────────────┐
            │  Transcript   │   │   Outcome    │
            │  完整执行记录  │   │  环境最终状态  │
            └──────────────┘   └──────────────┘
                    │                   │
                    └─────────┬─────────┘
                              ▼
                    ┌──────────────────┐
                    │     Grader       │
                    │   评分与判定      │
                    └──────────────────┘
```

### 三个核心阶段

**阶段一：Evaluation Suite — 准备"考卷"**

评测套件是一批 Task 的集合，每个 Task 自带 Grader（评分标准）。这不是随便出的题，而是从真实失败案例中提炼的。20-50 个真实失败案例就够启动，来源优先选已经在手动检查的内容。

**阶段二：Agent Harness + Trial — 执行"考试"**

Agent Harness 是被测 Agent 的运行框架，Trial 是一次完整的运行实例。同一个 Task 可以跑多次（对应 Pass@k / Pass^k），每次 Trial 都在独立环境中执行。

**阶段三：Transcript + Outcome → Grader — "阅卷"**

这一步最容易被做错。产出物分两条路径：
- **Transcript**：Agent 每一轮说了什么、调了什么工具、工具返回了什么——这是"执行过程"
- **Outcome**：环境最终变成了什么样——这是"实际结果"

### 关键判断：两条路径必须同时覆盖

只看 Transcript 会漏掉"说了但没做到"的情况，只看 Outcome 又看不出中间步骤是否走歪了。

Anthropic 的机票预订例子完美说明这一点：Opus 4.5 发现航空公司政策漏洞，找到了比预期更便宜的方案。如果只按预设执行路径（Transcript）打分，会被判失败；但看最终结果（Outcome），用户实际拿到了更好的方案。**只盯一面都会产生误判。**

## 三、两个核心指标及其适用场景

| 指标 | 定义 | 语义 | 适用场景 |
|------|------|------|---------|
| **Pass@k** | k 次运行中至少一次正确 | "理论上能不能做到" | 开发阶段，探索能力上限 |
| **Pass^k** | k 次运行中全部正确 | "每次都能不能做到" | 上线回归，保证稳定性 |

### 为什么不能混用

- 回归测试用了 Pass@k（过松）→ 不稳定的 Agent 也能通过，线上事故
- 能力评测用了 Pass^k（过严）→ 偶发的环境噪声就触发告警，团队疲于奔命

正确做法：**开发阶段用 Pass@k 验证能力边界，上线前用 Pass^k 保证回归质量，两者各司其职。**

## 四、三类评分器的选择逻辑

```
有明确正确答案？
    ├─ 是 → 代码评分器（确定性最高，优先选用）
    │       例：单元测试 pass/fail、字符串匹配、结构比对
    │
    └─ 否 → 需要判断语义质量？
              ├─ 是 → 模型评分器
              │       例：按评分标准打分、两答案对比选优、多模型投票
              │
              └─ 拿不准 → 人工评分器（标注一批来校准自动 judge 的漂移）
```

### 代码评分器为什么最优先

代码评分器最不容易因设计不当引入噪声——结果只有 pass/fail，不存在主观判断。而且它可以被版本控制、被复用、被批量执行。任何有明确正确答案的任务，都应该优先编码为代码评分器。

### 模型评分器的校准问题

模型评分器的风险在于**评分标准漂移**——同一个回答，今天打 8 分，明天可能打 6 分。解决方法：
- 用人工标注的黄金数据集定期校准
- 多个 LLM 投票取共识，降低单模型偏差
- 评分标准写具体，不要给模糊的 rubric

## 五、从零搭建评测体系的实操路径

### 第一步：验收定义先行

> 如果两个领域专家拿同一个案例独立判断，结论不一致，说明验收标准还没写清楚。

在收集数据之前，先把"什么叫对、什么叫错"定义到两个人能独立判断一致的程度。

### 第二步：环境隔离

每次 Trial 必须从干净状态开始。测试之间不能共享缓存、临时文件、数据库。否则一个任务的失败会污染下一个，表面看是模型问题，实际是环境脏了。

### 第三步：正例 + 反例双覆盖

只测"应该做 X"→ 评分器只会往一个方向优化。必须加入"不应该做 X 的情况"，才能发现边界行为是否正常。

### 第四步：定期读完整 Trace

不要只看聚合分数。评分器本身的 bug 通常只有在看具体 Trace 时才会暴露——比如某个 Grader 的正则写错了，把正确的答案判成失败，聚合分数看不出来。

### 第五步：持续升级难度

评测套件通过率接近 100% 不是好事——意味着它已经不能区分能力差异了。要定期补充更难的任务，保持评测的区分度。

## 六、最关键的原则：先修评测，再改 Agent

这是整个评测模块最核心的一条判断：

> **看到评测分数下降，先查环境，再动 Agent。**

评测系统常见的出错来源和表现：

| 问题 | 表现 | 容易误判为 |
|------|------|-----------|
| 运行环境资源不足 | 进程被杀，Trial 记失败 | 模型能力退化 |
| 评分器自身有 bug | 正确答案被判失败 | Agent 变差了 |
| 测试用例与生产脱节 | 评分与实际体验不匹配 | 需要优化 Prompt |
| 只看聚合分数 | 某类任务系统性变差被平均掉 | 整体还行的错觉 |

文章引用的数据说明问题：评测容器的资源限制越严，基础设施错误率（红色）越高，模型得分（蓝色）越低；放开资源限制后，红色跌到接近 0，蓝色几乎不变。**之前的"失败"大多是环境噪声，不是模型问题。**

基于失真信号去改 Agent，方向可能从一开始就是错的，甚至会把本来正常的部分改坏。

## 七、在线评测的采样策略

全量跑成本太高，完全随机采样又容易错过关键案例。推荐对 10%-20% 的 Trace 按规则路由采样：

| 采样触发条件 | 采样比例 | 逻辑 |
|-------------|---------|------|
| 用户负反馈 | 100% | 用户明确不满意，必查 |
| 高成本对话（token 超阈值） | 优先 | 往往代表 Agent 在绕圈子 |
| 时间窗口随机采样 | 按比例 | 保持对正常流量的覆盖 |
| 模型或 Prompt 变更后 | 头 48h 全量 | 确认没有退化 |

## 八、Agent Harness vs Evaluation Harness

回到全景图中的两个 Harness，它们的职责完全不同：

| | Agent Harness | Evaluation Harness |
|---|---|---|
| **角色** | 被测系统（"考生"） | 评测设施（"考务系统"） |
| **职责** | 带着约束去执行任务 | 出题、监考、收卷、打分 |
| **包含** | Agent Loop、工具集、安全边界 | Task 分发、Trial 管理、Grader 调度、结果汇总 |
| **关键设计** | 严格隔离，不能访问评测内部逻辑 | 不依赖 Agent 内部实现，保持通用性 |

两者必须**解耦**——Evaluation Harness 不能依赖 Agent Harness 的内部实现。否则换一个 Agent 框架就得重写评测，评测结果也不具备跨系统可比性。

---

## 九、总结

Agent 评测不是"加个打分环节"，而是一个独立的工程系统，有自己的架构（Suite → Harness → Trial → Grader）、自己的指标体系（Pass@k / Pass^k）、自己的质量保障（环境隔离 + Trace 审查 + 采样策略）。

核心要点回顾：

1. **评测结构比 Agent 本身复杂一个数量级**，不能套用传统 Single-turn 的思路
2. **Transcript 和 Outcome 必须双覆盖**，只看一面都有盲区
3. **Pass@k 测能力上限，Pass^k 测上线质量**，不能混用
4. **评分器选择按优先级**：代码 > 模型 > 人工
5. **先修评测，再改 Agent**，基于失真信号调整方向只会越改越差
6. **评测套件要持续升级难度**，通过率 100% 意味着评测已经失效
