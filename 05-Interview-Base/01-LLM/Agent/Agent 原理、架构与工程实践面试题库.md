## 一、基础概念与原理

### 1.1 Agent Loop 核心机制

**题目 1：请解释 Agent Loop 的基本运转方式，它的四个核心阶段是什么？**

**参考回答**：

Agent Loop 的核心运转方式是一个「感知 → 决策 → 行动 → 反馈」的循环过程。模型接收用户输入后，会经历以下四个阶段：

1. **感知（Perceive）**：Agent 接收并理解当前上下文中的所有信息，包括用户输入、历史消息、工具返回结果等

2. **决策（Reason）**：模型基于当前上下文进行推理，决定下一步应该采取什么行动，包括是否调用工具、调用哪个工具、传递什么参数

3. **行动（Act）**：Agent 执行决策，可能调用外部工具（如搜索、执行代码、访问 API）或直接生成文本回复

4. **反馈（Feedback）**：工具执行结果返回给 Agent，形成新的上下文，Agent 继续下一轮决策

这个循环会持续进行，直到模型判断任务已完成，不再需要调用工具，最终输出纯文本响应。

最小实现的 Agent Loop 核心逻辑不到 20 行代码，但这个循环本身相当稳定，从最小实现扩展到支持子 Agent、上下文压缩和 Skills 加载，主循环基本不需要变化。

---

**题目 2：Agent 和 Workflow 的本质区别是什么？什么时候应该选择哪种模式？**

**参考回答**：

两者的核心区别在于「控制权的归属」：

| 维度 | Workflow | Agent |
| --- | --- | --- |
| **控制权** | 代码预定义，同输入必走同一路径 | LLM 动态决策，可能需要评测验证 |
| **执行方式** | 工具顺序固定，错误走预设分支 | 工具按需选择，模型可尝试自我修复 |
| **状态与记忆** | 显式状态机，节点跳转清晰 | 隐式上下文，状态在对话历史中累积 |
| **维护成本** | 改流程需修改代码并重新部署 | 调整系统提示即可，无需重新部署 |
| **可观测性** | 日志定位节点，延迟可预估 | 需完整执行记录理解决策链，轮数不固定 |

**选择建议**：

- 选择 **Workflow**：任务流程固定、输入边界清晰、需要精确控制执行路径的场景

- 选择 **Agent**：需要中间推理、灵活判断、动态规划能力的场景

现实中很多标着「Agent」的产品，深入看其实更接近 Workflow，两者本身并无高下之分，真正重要的是为任务找到更适合的解决方案。

### 1.2 五种控制模式

**题目 3：请解释 LangChain 官网提到的五种常见 Agent 控制模式，并说明每种模式的适用场景。**

**参考回答**：

1. **提示链（Prompt Chaining）**：将任务拆解为顺序执行的步骤，每个 LLM 处理前一步的输出，中间可加代码检查点。适用于生成后翻译、先写大纲再写正文这类线性流程。

2. **路由（Routing）**：对输入进行分类，定向到对应的专用处理流程。简单问题走轻量模型，复杂问题走强模型，技术咨询和账单查询走不同逻辑。

3. **并行（Parallelization）**：

   - 分段法：把任务拆成独立子任务并发执行

   - 投票法：把同一任务跑多次取共识\
     适用于高风险决策或需要多视角的场景。

4. **编排器-工作者（Orchestrator-Workers）**：中央 LLM 动态分解任务，委派给工作者 LLM，综合结果。nanobot 的 `spawn` 工具和 learn-claude-code 的子 Agent 模式都是这个原型。

5. **评估器-优化器（Evaluator-Optimizer）**：生成器产出结果，评估器给出反馈，循环直到达标。适用于翻译、创意写作这类质量标准难以用代码精确定义的任务。

## 二、上下文工程

### 2.1 上下文管理核心问题

**题目 4：为什么说「上下文工程决定 Agent 稳定性」？Transformer 的注意力机制与上下文长度有什么关系？**

**参考回答**：

这个判断基于 Transformer 的核心机制：注意力复杂度是 **O(n²)**，这意味着随着上下文变长，每个 token 需要计算的注意力权重呈平方增长。

实践中最常见的失效模式是：**无关内容一旦占到上下文的大头，Agent 的决策质量就会明显下滑**。这类现象通常被称为「Context Rot」——上下文腐烂。

具体问题表现为：

- 偶尔用的东西每次都加载进来，信息密度降低

- 稳定的规则和动态的状态混在一起

- 模型能看到的内容越来越多，但真正有用的部分越来越难被注意到

所以问题通常不是窗口不够长，而是**信息密度不对**。解决方式是按信息的使用频率和稳定性分层管理，每层只放自己该放的东西。

---

**题目 5：请解释三种常见上下文压缩策略的原理、优缺点和适用场景。**

**参考回答**：

| 策略 | 成本 | 丢失内容 | 适用场景 |
| --- | --- | --- | --- |
| **滑动窗口** | 极低 | 早期上下文 | 简短对话 |
| **LLM 摘要** | 中 | 细节，保留决策 | 长任务、含关键决策 |
| **工具结果替换** | 极低 | 工具原始输出 | 工具调用密集型 |

**进阶做法**：

- **Branch Summarization**：摘要时明确保留架构决策、未完成任务和关键约束

- **micro_compact**：每轮替换旧工具输出

- **auto_compact**：上下文超阈值时自动触发

**重要提醒**：压缩阶段最常见的问题不是摘要不够短，而是**保留顺序设错了**。LLM 通常会优先删除那些看起来还可以重新获取的信息，早期的 tool output 通常最先被移除，但与之相关的架构决策、约束理由和失败路径也很容易一并丢失。最好在 `CLAUDE.md` 里明确写出压缩时的保留优先级。

### 2.2 Prompt Caching 与 Skills

**题目 6：什么是 Prompt Caching？它的实现原理是什么？缓存命中的前提条件是什么？**

**参考回答**：

**实现原理**：LLM 推理时，Transformer attention 会为每个 token 计算 Key-Value 对。如果当前请求的输入前缀和之前某次请求完全一致，这部分 KV 就不需要重新计算，直接从缓存读取，这就是 Prompt Caching 的底层原理。

**命中前提**：**精确前缀匹配**，不是内容相似就能触发。任何一个 token 不同都会破坏匹配。

**设计原则**：

- 系统提示、工具定义、长文档这类在多轮请求里基本不变的内容天然适合缓存

- 动态信息（当前时间、用户输入、工具调用结果）放在后面，不影响前缀的稳定性

- 常驻层越稳定，前缀命中率越高，边际成本越低

- 稳定的大系统提示比频繁变动的小提示实际成本更低，因为写入成本只付一次，后续每次调用读取的折扣可以达到 **90%**

---

**题目 7：Skills 延迟加载的核心思路是什么？有效的 Skill 描述符应该怎么写？**

**参考回答**：

**核心思路**：系统提示只保留索引，完整知识按需加载。

**有效 Skill 描述符的写法**：

- 足够短，避免常驻上下文持续涨 token

- 足够像路由条件而不是功能介绍

- 至少说明：什么时候用、什么时候不要用、产出物是什么

- 最直接的写法：**Use when / Don't use when** 再补几条反例

**关键数据**：没有反例时准确率从基准 73% 掉到 53%，加上反例后升到 **85%**，响应时间还降了 **18.1%**。反例不是可选项，是 Skill 描述能不能起作用的关键。

**常见陷阱**：

- 描述太短（`help with backend`）等于任何后端工作都能触发，路由会乱

- 路由准确率差距不大，但每个启用的 Skill 描述符都常驻上下文，Skill 一多，累积成本很可观

- 真正有效的描述符是路由条件，不是功能介绍

## 三、工具设计

### 3.1 ACI 原则

**题目 8：什么是 ACI（Agent-Computer Interface）？它与传统的 API 封装有什么区别？**

**参考回答**：

**演进历程**：

- **第一代（API 封装）**：每个 API Endpoint 对应一个工具，粒度过细，Agent 往往需要协调多个工具才能完成一个目标

- **第二代（ACI）**：工具应对应 Agent 的目标，而不是底层 API 操作

- **Advanced Tool Use**：优化工具的发现、调用和描述方式

**ACI 核心区别**：

| 维度 | API 封装 | ACI |
| --- | --- | --- |
| **粒度** | 对应 API 能做的操作 | 对应 Agent 要完成的目标 |
| **示例** | `get_post + update_content + update_title` | `update_yuque_post` |
| **返回** | 完整原始数据 | 与下一步决策直接相关的字段 |
| **错误** | 通用字符串 “Error” | 结构化，含修正建议 |
| **描述** | 只写功能说明 | 说明何时用、何时不用 |

**ACI 示例**：

```javascript
const updateTool = betaZodTool({
  name: "update_yuque_post",
  description: "更新语雀文章内容，不适合创建新文章",
  inputSchema: z.object({
    post_id: z.string().describe("语雀文章 ID，纯数字字符串，如 '12345678'"),
    title: z.string().optional().describe("文章标题，不改时可省略"),
    content_markdown: z.string().describe("Markdown 格式正文"),
  }),
  run: async (input) => {
    const post = await getPost(input.post_id);
    if (!post) throw new ToolError("文章 ID 不存在", {
      error_code: "POST_NOT_FOUND",
      suggestion: "请先调用 list_yuque_posts 获取有效的 post_id",
    });
    return await updatePost(input.post_id, input.title, input.content_markdown);
  },
});
```

### 3.2 工具设计最佳实践

**题目 9：调试 Agent 行为时，应该优先检查什么？为什么大多数工具选择错误的原因不在模型能力？**

**参考回答**：

应该**优先检查工具定义**。这个判断可能有违直觉——很多人会首先怀疑模型能力不够，但实际经验表明：

1. **工具描述不准确是主要问题源**：工具只说自己能做什么，不说明什么时候该用、什么时候不该用，结果是 Agent 容易选错工具、填错参数，报错后不断重试绕圈

2. **工具问题的表现形式**：

   - 选不对工具

   - 描述看不懂

   - 返回一堆没用的

   - 出了错 Agent 不知道怎么改

3. **解决思路**：

   - 工具描述要说明边界：「何时用」比「能做什么」重要

   - 返回结构化错误，给出修正建议

   - 用 Zod 等工具把定义和实现绑定，问题尽量在编译期暴露

   - 工具数量要克制，能用 Shell 处理的、只需静态知识的、更适合 Skill 的，都不需要新增工具

---

**题目 10：工具消息为什么要隔离？具体实现方式是什么？**

**参考回答**：

**问题背景**：框架运行过程中会产生一些内部事件（压缩发生了、通知推送了、某个工具调用被跳过等），这些事件需要记在会话历史里，但不应该直接进入 LLM，否则模型会看到一堆它不理解的字段，白白消耗 token。

**解决方式**：在框架层分两种消息类型：

- `AgentMessage`：给应用层用，可以携带任意自定义字段

- `Message`：真正发给 LLM 的，只保留 `user`、`assistant`、`tool_result` 三种标准类型

调用前过滤一遍，会话历史保留完整框架状态，LLM 只收它需要的部分。

## 四、记忆系统

### 4.1 记忆分层设计

**题目 11：Agent 的记忆系统通常分为哪四种？它们分别存储在哪里？各有什么特点？**

**参考回答**：

| 记忆类型 | 存储位置 | 持久化 | 特点 |
| --- | --- | --- | --- |
| **上下文窗口** | messages[] | 否 | 会话级，session 结束即清空 |
| **Skills 文件** | 文件系统 | 是 | 按需加载，不常驻 |
| **JSONL 会话历史** | 磁盘 | 是 | 完整过程保留，可检索 |
| [**MEMORY.md**](http://MEMORY.md) | 磁盘 | 是 | 沉淀稳定事实，跨会话注入 |

**关键设计原则**：

- Agent 不具备原生的时间连续性，记忆层需要单独设计

- 重要事实要留下来，注入模型的内容又不能失控

- 对大多数 Agent 来说，记忆库规模并不需要一开始就引入向量存储，结构化 Markdown 加关键词搜索已经具备足够好的可调试性、可维护性和成本表现

---

### 4.2 记忆整合机制

**题目 12：请解释记忆整合的触发机制和回退策略。为什么说流程必须可回退？**

**参考回答**：

**触发机制**：当 token 占用超过 **50% 阈值**时触发整合，成功路径：

1. 对待整合消息做 `llmSummarize(toConsolidate)`

2. 把摘要追加到 `MEMORY.md`

3. 只更新 `lastConsolidatedIndex`

**失败路径**：把原始消息写入 `archive/`，保留完整历史，避免整合失败时丢失上下文。

**为什么必须可回退**：

- 最关键的不是摘要写得多漂亮，而是流程本身必须可回退

- 系统只移动指针，不删除原始消息

- 即使整合失败，也还能回到原始存档继续工作

- 这不是「把旧消息删掉」，而是「从活跃上下文中安全移出」

## 五、多 Agent 组织

### 5.1 协作模式

**题目 13：多 Agent 系统中「指挥者模式」和「统筹者模式」有什么区别？各自适用于什么场景？**

**参考回答**：

| 模式 | 特点 | 产出物 | 适用场景 |
| --- | --- | --- | --- |
| **指挥者模式** | 同步协作，人与单个 Agent 紧密互动 | 短暂的对话产出 | 需要人实时介入调整决策的任务 |
| **统筹者模式** | 异步委派，人在起点和终点出现 | 分支、PR 等可持久化工件 | 需要多个 Agent 并行工作的复杂任务 |

**多 Agent 的主要价值**：不是单纯多开几个模型，而是把人的持续参与，变成对工件的最终审核。

**常见组织方式**：主 Agent 作为 Orchestrator 统筹全局，下挂多个子 Agent 独立并行工作，通过 JSONL inbox 协议通信，用 Worktree 隔离文件修改，用任务图管理依赖关系。

---

### 5.2 协作协议与安全

**题目 14：为什么多 Agent 协作必须写成协议？协议至少需要包含哪些内容？**

**参考回答**：

**原因**：多 Agent 协作一旦靠自然语言来对齐，很快就会出问题。模型记不稳谁承诺了什么，也记不稳谁在等谁的结果。

**协议至少需要三样东西**：

1. **通信协议**：主 Agent 通过 JSONL 消息队列分派任务给子 Agent，子 Agent 执行后只回摘要，搜索和调试细节留在自己的独立上下文里

2. **任务图**：`.tasks/` 记录任务图和依赖关系

3. **隔离边界**：`.worktrees/` 隔离每个子 Agent 的文件修改

**执行顺序**：协议先定，隔离先做，再谈协作和并行。

---

**题目 15：多 Agent 系统中，幻觉问题会如何放大？如何缓解这个问题？**

**参考回答**：

**问题**：多个 Agent 频繁互动时，错误也会被一层层放大：

- Agent A 先带偏

- Agent B 跟着强化

- Agent C 再继续叠加

- 最后所有 Agent 都收敛到同一个高置信度的错误结论

**缓解方案**：**交叉验证**能打断这条错误传播链，让某个 Agent 独立判断，而不是顺着前面的结论继续走。

**引入顺序**：

1. 先有可持久化任务图

2. 再引入有身份的队友

3. 再引入结构化通信协议

4. 最后再加交叉验证或外部反馈（如独立的第二个 Agent、单元测试、编译器、人工审查）

## 六、评测系统

### 6.1 Agent 评测的特殊性

**题目 16：为什么 Agent 评测比传统 Single-turn 评测更复杂？请解释评测的核心要素和结构。**

**参考回答**：

**传统评测 vs Agent 评测**：

- 传统：一个 Prompt 进去，模型输出一个 Response，判断对否就结束

- Agent：需要先准备好工具和运行环境，Agent 在执行过程中多次调用工具、修改环境状态，最终评分不是看它说了什么，而是跑一批测试验证环境里真正发生了什么

**核心三组概念**：

1. **task**（任务）、**trial**（单次运行）、**grader**（评分器）

2. **transcript**（完整执行记录）和 **outcome**（环境最终结果）

3. **agent harness**（被评测的 Agent 运行框架）和 **evaluation harness**（评测基础设施）

**重要提醒**：

- 「看 Agent 怎么说」和「看系统最后变成什么样」是两件事

- Agent 说「订票已完成」是在看执行记录 transcript

- 数据库里确实生成了一条订单这是在看最终结果 outcome

- 只看执行记录会漏掉「说了但没做到」，只看最终结果又可能看不出中间步骤走歪了，两类都要覆盖

---

### 6.2 评测指标与评分器

**题目 17：请解释 Pass @k 和 Pass^k 的区别，它们分别适用于什么场景？**

**参考回答**：

| 指标 | 含义 | 场景 |
| --- | --- | --- |
| **Pass @k** | k 次至少一次正确 | 探索能力上限，能力突破时重跑 |
| **Pass^k** | k 次全部正确 | 上线回归，每次变更都跑 |

**混用风险**：

- Pass^k 过松会漏掉问题（回归测试）

- Pass @k 过严会让每次小改动都告警（能力评测）

---

**题目 18：三类评分器（代码评分器、模型评分器、人工评分器）各有什么特点？应该按什么顺序选择？**

**参考回答**：

| 类型 | 典型做法 | 确定性 | 适用场景 |
| --- | --- | --- | --- |
| **代码评分器** | 字符串匹配、单元测试 pass/fail、结构比对、工具调用参数验证 | 最高 | 有明确正确答案的任务 |
| **模型评分器** | 按评分标准打分、两个答案对比选优、多个模型投票取共识 | 中 | 语义质量、风格、推理过程 |
| **人工评分器** | 专家抽样审查、标注队列校准 | 可靠但慢 | 建立基准、校准自动 judge |

**选择顺序**：

1. 有明确正确答案 → 优先用代码评分器

2. 需要判断语义质量 → 再用模型评分器

3. 遇到拿不准的案例 → 人工标注一批，用来校准自动评分器的漂移

---

### 6.3 评测体系构建

**题目 19：如何从零搭建 Agent 评测体系？应该从什么地方开始？**

**参考回答**：

**启动规模**：不用等有了完整体系再开始，**20 到 50 个真实失败案例**就够启动。

**案例来源**：优先选已经在手动检查的内容，那些才是真正反映实际用途的。

**前置判断标准**：如果两个领域专家拿同一个案例独立判断，结论不一致，这个案例的验收标准就还没写清楚，先解决定义，再收集数据。

**关键步骤**：

1. 环境隔离：每次运行都要从干净状态开始，测试之间不能共享缓存、临时文件或数据库状态

2. 测试用例要同时覆盖正例和反例

3. 定期读完整执行记录，不要只看聚合分数，评分器本身的 bug 通常只有在看具体 Trace 时才会暴露

4. 当通过率接近 100% 时补充更难的任务

---

### 6.4 评测系统问题排查

**题目 20：为什么看到 Agent 表现下降时，应该优先检查评测系统本身而不是 Agent 代码？**

**参考回答**：

**核心原因**：评测系统出问题了，拿到的是一个**失真的信号**，基于它去改 Agent，改的方向可能从一开始就是错的，甚至会把本来运行正常的部分改坏。

**评测系统常见的出错来源**：

1. 运行环境资源不足导致进程被杀

2. 评分器本身有 bug 把正确答案判成失败

3. 测试用例和生产场景脱节

4. 只看聚合分数而漏掉某一类任务系统性变差

**排查方法**：红色是基础设施错误率，蓝色是模型得分。资源上限越严，环境越容易在内存峰值时崩掉，评测直接记失败，但模型其实没答错。随着上限放开，红色跌到接近 0，蓝色几乎不变，说明之前的「失败」不少是环境噪声。

**结论**：看到评测分数下降，**先查环境，再动 Agent**。

## 七、可观测性与追踪

### 7.1 Trace 核心要素

**题目 21：Agent 的 Trace 系统需要记录哪些关键信息？为什么传统 APM 往往帮助有限？**

**参考回答**：

**需要记录的核心信息**：

- 完整执行记录（每个 turn 的输入输出）

- 工具调用详情（名称、参数、返回结果、执行时间）

- 决策理由（模型为什么选择这个工具）

- 上下文状态变化（记忆整合、压缩等事件）

- 错误与异常信息

**为什么传统 APM 帮助有限**：

- 接口层看起来可能一切正常

- 真正的问题出在模型某一轮做出了错误决策

- 只有回看完整 Trace 才能定位

**扩展能力**：条件允许的话，这套系统还应具备语义检索能力，能够查询「哪些 Trace 里 Agent 混淆了两种工具」这类问题。

---

### 7.2 两层可观测性

**题目 22：请解释 Agent 可观测性的两层架构设计，以及各自的职责。**

**参考回答**：

**第一层：人工抽样标注**

- 基于规则采样错误案例、长对话和用户负反馈

- 由人工判断执行质量和失败原因

- 主要用来摸清失败模式，并给第二层提供校准数据

**第二层：LLM 自动评估**

- 对更大范围的 Trace 做全量覆盖

- 以第一层标注结果作为校准依据

- 只跑第二层，评分标准很容易漂移

- 只靠第一层，规模上又覆盖不了真实流量

两层要一起用，才能既保证规模覆盖，又保持评分质量。

## 八、工程实践

### 8.1 Harness 核心组成

**题目 23：OpenAI 的 Agent 优先开发实践中，Harness 包括哪些部分？为什么说 Harness 比模型更关键？**

**参考回答**：

**Harness 包含四个部分**：

1. **验收基线**：测试用例和评分标准

2. **执行边界**：约束条件（资源限制、时间限制、权限控制）

3. **反馈信号**：自动化验证机制

4. **回退手段**：出错时的恢复策略

**为什么 Harness 更关键**：

- 模型虽然重要，但决定系统能不能稳定运行的，往往是这些外围工程条件

- 这个判断在代码编写这类高可验证任务上最成立

- 但在开放式研究、多轮协商这类弱验证任务里，模型上限本身仍然更关键

---

### 8.2 安全边界设计

**题目 24：Agent 安全边界设计需要考虑哪些方面？请以 OpenClaw 为例说明。**

**参考回答**：

**三件必须先到位的事**：

1. **谁能用 → 白名单授权**

   - 只有授权用户可以触发 Agent

2. **能在哪用 → 工作空间隔离**

   - shell 工具需要强制进行路径检查

   - 越出工作空间目录就直接报错

3. **做了什么可以追踪 → 操作审计日志**

   - 每次执行都记一笔，方便后续审计和排查

**两层额外兜底**：

- **Prompt Injection**：按 source-sink 拆，把外部内容明确标成「不可信输入」，不要和系统提示混在一起

- **Provider 故障切换**：当前 Provider 挂了就自动切下一个，不用人盯

---

### 8.3 长任务处理

**题目 25：如何让 Agent 长任务能够跨 Session 继续？具体实现方式是什么？**

**参考回答**：

**问题**：长任务最常见的失败，不是单步报错，而是 session 结束时任务还没做完。

**解决方式**：把长任务拆成 **Initializer Agent** 和 **Coding Agent** 两个角色协作：

**Initializer Agent**（第一轮运行一次）：

- 生成 `feature-list.json`

- 生成 `init.sh`

- 创建初始 git commit

- 创建 `claude-progress.txt`

**Coding Agent**（多个 session 循环执行）：

- 每次从 `claude-progress.txt` 和 `git log` 恢复现场

- 定位当前任务

- 实现一个功能，跑测试

- 更新 `passes` 字段

- 提交代码后退出

**关键设计**：

- 进度要放在文件里，不要放在上下文里

- 功能清单用 JSON，不用 Markdown

- 当 `feature-list.json` 里所有功能都变成 `passes: true`，任务才算完成

## 九、常见反模式

### 9.1 工程问题识别

**题目 26：请列举至少 5 个 Agent 开发中的常见反模式，并说明如何修复。**

**参考回答**：

| 反模式 | 问题 | 修复方案 |
| --- | --- | --- |
| **系统提示当知识库** | 越来越长，关键规则被忽略 | 约定留在系统提示，领域知识移到 Skills |
| **工具数量失控** | Agent 频繁选错工具 | 合并重叠工具，明确命名空间 |
| **缺少验证机制** | Agent 说完成了，但没法验证 | 每类任务绑定可执行的验收标准 |
| **多 Agent 无边界** | 状态漂移，故障归因困难 | 明确角色和权限，worktree 隔离，设置 maxTurns |
| **记忆不整合** | 长对话第 20 轮后决策质量下降 | 监控 token 占用，超阈值自动触发整合 |
| **没有评测** | 改了一个地方不知道有没有引入回归 | 每个真实失败案例立刻转成测试用例 |
| **过早引入多 Agent** | 协调开销超过并行收益 | 先建任务图，验证单 Agent 上限后再扩展 |
| **约束靠期望不靠机制** | 规则在文档里，Agent 选择性遵守 | 期望 → 工具验证 / Linter / Hook |

---

### 9.2 工程落地顺序

**题目 27：Agent 工程实现的推荐顺序是什么？为什么是这个顺序？**

**参考回答**：

**推荐顺序**：

1. **单渠道先跑通** — Telegram → Agent → Telegram 完整链路，不要第一版就抽象多渠道

2. **安全边界先于功能** — 工作空间隔离、白名单、参数验证，加任何新功能之前就要到位

3. **记忆整合要早做** — 不加整合，第 20 轮对话之后基本就垮了

4. **Skills 先于新工具** — 领域知识用文档管理，比加新工具更灵活

5. **第一个失败就建评测** — 把第一个真实失败案例转成测试用例，不要等积累够了再开始

## 十、综合问题

### 10.1 架构设计能力

**题目 28：如果让你设计一个支持多渠道接入、可扩展的 Agent 系统，你会如何设计？请以分层架构说明。**

**参考回答**：

**五层解耦架构**（以 OpenClaw 为例）：

| 层级 | 实现 | 主要职责 | 关键设计决策 |
| --- | --- | --- | --- |
| **Gateway** | WebSocket 服务 | 接住外部连接，统一路由消息和系统控制信号 | Channel 和 Agent 不直接通信，统一走 Gateway |
| **Channel 适配器** | 23+ 渠道 | 对接 Telegram、Discord 等不同渠道 | 新增渠道不修改 Agent 代码 |
| **Pi Agent** | 可调用服务 | 维护 Agent 主循环、会话状态、调度和工具调用 | 与渠道完全解耦，支持流式工具调用 |
| **工具集** | shell/fs/web/browser/MCP | 提供外部能力 | 按 ACI 原则设计，面向任务目标 |
| **上下文+记忆** | Skills + [MEMORY.md](http://MEMORY.md) | 管理上下文和跨会话记忆 | 50% 阈值自动触发整合 |

**消息总线的作用**：Channel 只管收发，AgentLoop 只管处理，互不干扰，加上定时任务后，系统不再只有用户消息这一个入口。

---

### 10.2 优化决策能力

**题目 29：如果发现 Agent 的决策质量下降，你会从哪些方面排查问题？请列出排查清单。**

**参考回答**：

**排查清单**：

1. **上下文层面**

   - 检查 token 占用是否超过阈值

   - 检查是否存在 Context Rot（无关内容占比过高）

   - 检查压缩策略是否丢失了关键信息

   - 检查是否有大段无用的工具返回

2. **工具层面**

   - 检查工具定义是否清晰（描述是否说明边界）

   - 检查工具返回是否结构化、包含修正建议

   - 检查工具数量是否过多导致注意力稀释

3. **模型层面**

   - 检查系统提示是否稳定（频繁变化会破坏缓存）

   - 检查 Skills 加载是否正确

4. **记忆层面**

   - 检查 [MEMORY.md](http://MEMORY.md) 是否有重要事实沉淀

   - 检查记忆整合是否正常工作

   - 检查是否存在跨会话状态丢失

5. **评测层面**

   - **先检查评测系统本身是否准确**

   - 检查环境是否干净（是否存在资源不足问题）

   - 检查评分器是否有 bug

---

### 10.3 技术判断能力

**题目 30：有一个观点认为「更贵的模型能带来显著的 Agent 效果提升」，请基于文章内容评价这个观点，并说明你的看法。**

**参考回答**：

**文章观点**：更贵的模型带来的提升，**很多时候没有想象中那么大**，反而 Harness 和验证测试质量对成功率的影响更大。

**支撑论据**：

1. OpenAI 的 Agent 优先开发实践：3 个工程师 5 个月写了百万行代码，将近 1500 个 PR，是传统开发速度的 10 倍。这个速度背后不是模型有多强，而是工程决策做对了。

2. 调试 Agent 行为时，应优先检查工具定义，因为多数工具选择错误都出在描述不准确，不在模型能力。

3. 评测系统本身的问题很多时候比 Agent 出问题更难发现，如果一直在 Agent 代码上反复调，效果未必明显。

**我的看法**：

- 模型能力仍然是基础，但没有配套的工程基础设施，模型能力无法充分发挥

- 在高可验证任务（如代码编写）上，Harness 的影响更显著

- 在弱验证任务（如开放式研究）上，模型上限仍然更关键

- 投资优先级应该是：先把基础工程设施搭好，再考虑模型升级
