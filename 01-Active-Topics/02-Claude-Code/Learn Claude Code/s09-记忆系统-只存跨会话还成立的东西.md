# s09: 记忆系统 - 只存跨会话还成立的东西

> *"memory 提供方向，不替代当前观察"*

## 要解决的问题

没有 memory 的 agent 每次新会话从零开始：

- 用户长期偏好，每次都要重新说
- 被纠正过的错误，下次照样犯
- 不容易从代码看出来的项目约定，永远不知道
- 外部资源在哪，每次都要重新找

## 什么不该进 memory

这比"该存什么"更重要。
	
| 不存的东西 | 理由 |
|-----------|------|
| 文件结构、函数签名、目录布局 | 重新读代码就能得到 |
| 当前任务进度 | task/plan 的事 |
| 临时分支名、当前 PR 号 | 很快过时 |
| 修 bug 的具体代码细节 | 代码和提交记录才是准确的 |
| 密钥密码凭证 | 安全风险 |

只对这次任务有用的不存，从代码能重新推导的不存，很快会过时的不存。

## 4 类 memory

| 类型 | 存什么 | 举例 |
|------|--------|------|
| user | 用户偏好 | 代码风格、回答详细程度、工具链选择 |
| feedback | 纠正过的错误和验证过的做法 | "不要 mock 数据库"、"这种方案之前验证过没问题" |
| project | 不容易从代码重新推导的项目背景 | 某设计因合规要求、某目录短期不能动 |
| reference | 外部资源指针 | 问题单在哪个看板、监控面板在哪 |

feedback 不只来自负反馈。某种做法被用户沉默认可了，也值得记。只存纠错不存确认，系统会越来越保守。

## memory 和 task/plan/CLAUDE.md 的边界

按生命周期区分：

```
task/plan  →  小时级，只对这次任务有用
memory     →  天级，很多会话可能都有用
CLAUDE.md  →  月级，长期固定说明
```

memory 和 compact（s06）也是两套机制。compact 压缩当前会话的上下文，memory 跨会话持久化。

## 存储结构

```
.memory/
  ├── MEMORY.md              # 索引，最多 200 行
  ├── prefer_tabs.md         # 单条 memory
  ├── feedback_tests.md
  └── incident_board.md
```

单条 memory 格式：

```markdown
---
name: prefer_tabs
description: User prefers tabs for indentation
type: user
---

The user explicitly prefers tabs over spaces.
```

frontmatter 是元数据，正文是完整内容。MEMORY.md 是索引，不重复内容，只帮系统快速知道"有哪些 memory 可用"。

## MemoryManager 做了什么

### 加载

启动时扫描 `.memory/` 下所有 `.md`，解析 frontmatter，跳过 `MEMORY.md`：

```python
for md_file in sorted(self.memory_dir.glob("*.md")):
    if md_file.name == "MEMORY.md":
        continue
    parsed = self._parse_frontmatter(md_file.read_text())
    if parsed:
        name = parsed.get("name", md_file.stem)
        self.memories[name] = {
            "description": parsed.get("description", ""),
            "type": parsed.get("type", "project"),
            "content": parsed.get("content", ""),
            "file": md_file.name,
        }
```

`sorted()` 保证加载顺序稳定。`name` 缺失时用文件名（`md_file.stem`）兜底。

### frontmatter 解析

手写正则，没用 yaml 库：

```python
def _parse_frontmatter(self, text: str) -> dict | None:
    match = re.match(r"^---\s*\n(.*?)\n---\s*\n(.*)", text, re.DOTALL)
    if not match:
        return None
    header, body = match.group(1), match.group(2)
    result = {"content": body.strip()}
    for line in header.splitlines():
        if ":" in line:
            key, _, value = line.partition(":")
            result[key.strip()] = value.strip()
    return result
```

`re.DOTALL` 让 `.` 匹配换行，支持多行 frontmatter。代价是不支持多行值或嵌套结构——`description` 必须是单行的。和 s05 的 SkillLoader 用 `yaml.safe_load` 不同，教学版省了依赖。

### 保存

四步：校验类型 → 名称清洗 → 写文件 → 重建索引。

```python
safe_name = re.sub(r"[^a-zA-Z0-9_-]", "_", name.lower())
frontmatter = f"---\nname: {name}\ndescription: {description}\ntype: {mem_type}\n---\n{content}\n"
file_path.write_text(frontmatter)
self._rebuild_index()
```

名称清洗把非安全字符全替换成下划线。用户说"记住我对测试的看法"，文件名会变成 `____________.md`——教学版的简化，真实版用 Unicode 安全编码。

### 索引重建

```python
def _rebuild_index(self):
    lines = ["# Memory Index", ""]
    for name, mem in self.memories.items():
        lines.append(f"- {name}: {mem['description']} [{mem['type']}]")
        if len(lines) >= MAX_INDEX_LINES:  # 200
            lines.append(f"... (truncated at {MAX_INDEX_LINES} lines)")
            break
    MEMORY_INDEX.write_text("\n".join(lines) + "\n")
```

硬截断 200 行。索引在新会话时被加载到上下文，体积必须控制。

### 注入 system prompt

按类型分组输出：

```python
def load_memory_prompt(self) -> str:
    for mem_type in MEMORY_TYPES:  # user, feedback, project, reference
        typed = {k: v for k, v in self.memories.items() if v["type"] == mem_type}
        sections.append(f"## [{mem_type}]")
        for name, mem in typed.items():
            sections.append(f"### {name}: {mem['description']}")
            sections.append(mem["content"].strip())
```

每轮 LLM 调用都重建 system prompt：

```python
while True:
    system = build_system_prompt()  # 每轮重建
    response = client.messages.create(model=MODEL, system=system, ...)
```

同一会话内 `save_memory` 新增的条目，下一轮立刻可见。

MEMORY_GUIDANCE 常量拼进 system prompt，告诉模型什么该存什么不该存。存储边界靠提示词引导模型行为，不靠代码强制——save_memory 不检查内容是否真的属于该类型，全靠模型自律。

### save_memory 工具的 schema 设计

```python
"type": {
    "type": "string",
    "enum": ["user", "feedback", "project", "reference"],
    "description": "user=preferences, feedback=corrections,
     project=non-obvious project conventions, reference=external resource pointers"
}
```

把每种类型的含义直接写进 schema description。模型选类型时能看到提示，不需要额外解释。

## DreamConsolidator

教学版搭了框架没填逻辑。7 道门控决定是否触发整理：

| 门控 | 条件 | 目的 |
|------|------|------|
| enabled 标志 | 全局开关 | |
| memory 目录存在且有文件 | 没东西可整理 | |
| 不在 plan 模式 | plan 模式不跑整理 | |
| 距上次整理 > 24h | 冷却期 | |
| 距上次扫描 > 10min | 节流 | |
| session_count >= 5 | 样本太少不值得 | |
| PID 锁可用 | 防并发 |

PID 锁的实现值得看：

```python
def _acquire_lock(self) -> bool:
    if self.lock_file.exists():
        lock_data = self.lock_file.read_text().strip()
        pid_str, timestamp_str = lock_data.split(":", 1)
        pid = int(pid_str)
        lock_time = float(timestamp_str)
        # 过期超过 1 小时 → 删锁
        if (time.time() - lock_time) > self.LOCK_STALE_SECONDS:
            self.lock_file.unlink()
        else:
            # 进程还活着 → 锁有效
            os.kill(pid, 0)
            return False
    # 写新锁：PID + 时间戳
    self.lock_file.write_text(f"{os.getpid()}:{time.time()}")
```

锁文件内容是 `PID:timestamp`。`os.kill(pid, 0)` 发信号 0，不杀进程，只检测存在性。进程已死抛 OSError，锁被视为过期。过期 1 小时（`LOCK_STALE_SECONDS = 3600`），防止崩溃后锁永远不释放。

4 阶段整理：Orient（扫描索引）→ Gather（读文件）→ Consolidate（合并去重）→ Prune（截断索引）。教学版只打印阶段名，真实版会用 LLM 判断哪些该合并删除。

## 生产级系统要补的 6 条边界

教学版不实现，但设计者必须理解。

**1. 作用域分离：private vs team。** user 类型几乎总是 private，project 和 reference 偏 team。

场景：用户 A 告诉 agent"我讨厌 mock，测试必须打真数据库"。这条 feedback 如果提升到 team 作用域，用户 B 的 agent 也会遵守——但 B 可能觉得 mock 没问题。反过来，"这个目录不能动是因为合规要求"如果只存在 A 的 private 里，B 的 agent 不知道就可能动了。

作用域分错的后果不对称：个人偏好泄露到 team，最多是别人被不必要的规则约束；团队规则只锁在一个人手里，可能导致别人犯错。后者更危险。

**2. 正反馈也要存。** 负反馈通常是显式的，正反馈通常是隐式的——用户没反对就接受了某做法。

某次 agent 用了一种不太常见的方案解决了棘手问题，用户没说什么就直接采用了。这种沉默的认可如果不主动捕捉，下次遇到类似问题 agent 可能换一种"更标准"但用户不喜欢的方式。

只存纠错不存确认，系统每被纠正一次多一条限制，但从来没有一条记录告诉它"这个方向对，可以大胆走"。结果就是越来越保守。

* 特别是真实的业务场景，收集用户的点踩点赞信息时，如果做的好可能只是默认接受，很少主动点赞，如果做错了，点踩的情况也很难收集到完整、有用的反馈信息来支持 Agent 的正向循环

**3. 即使用户要求存，有些东西也不该存。** 本周 PR 列表、当前分支名、函数签名——时间敏感性高、变化频率快。存的时候是对的，几天后就变成错的。memory 的读取是跨会话的，下次加载时用户不会附带一句"这个可能已经过时了"。

不是直接拒绝，而是追问：这里面真正值得长期留下的、非显然的信息是什么？比如用户说"帮我记住这个 PR 列表"，追问之后可能发现真正想保留的是"这个项目用 conventional commits 格式"——这才是跨会话有价值的信息。

判断标准：如果一条信息在 30 天后大概率还是准确的，才值得存。

**4. memory 会漂移。** 漂移的来源：代码重构后函数换了位置、项目约定因新成员加入被修改、外部资源迁移了 URL、用户偏好本身发生了变化。

memory 里记着"测试都在 tests/ 目录下"。agent 直接告诉用户"把测试写到 tests/"，但项目已经迁移到 co-located 测试模式，用户按这个操作就放错了。

正确流程：

```
memory 提供方向 → 去当前状态验证 → 给用户结论
```

而不是 memory 直接给用户结论。memory 记录的是"曾经成立过的事实"，不是永久真理。

**5. 用户说忽略就当空的。** 有两种处理方式容易混淆：

方式 A："我知道 memory 里说了什么，但这次假装没看到。"——memory 内容仍然被读取了，只是被标记为忽略。但模型在后续推理中可能不自觉地被影响。

方式 B："memory 为空，按没有任何历史记忆的状态工作。"——从输入层面不加载 memory 内容。

应该选方式 B。LLM 的行为很难完全控制，让它"看到但忽略"，很难真正做到不受影响。代码里的实现含义是 `build_system_prompt()` 检查一个标志位，用户说了忽略就直接跳过 `memory_section` 的拼接。

**6. 推荐具体路径前再验证一次。** memory 里的信息分两类：

- 方向性信息："测试习惯用 pytest"、"部署用 GitHub Actions"——不太会错
- 具体性信息："入口在 src/main.py"、"看板在 linear.app/xxx"——容易过时

不是所有从 memory 读取的内容都需要验证。agent 在思考过程中参考方向性信息不需要确认。但一旦要把具体路径、函数名、URL 作为建议输出给用户，就应该先核验。

memory 的价值是提供"去哪找答案"的线索，不是答案本身。两步走：memory 告诉去哪验证，验证完再给用户结论。

## 初学者最容易犯的三个错

**把代码结构存进 memory。** "这个项目有 src/ 和 tests/"——重新读一遍就有了。

**把当前任务状态存进 memory。** "正在改认证模块"——这是 task，不是 memory。

**把 memory 当绝对真相。** memory 可能过时。和当前代码冲突时，优先相信你看到的真实状态。
