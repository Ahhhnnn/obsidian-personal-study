# Harness Engineering（驾驭工程）

> 核心公式：**Agent = Model + Harness**
> 模型提供智能，Harness 决定这份智能如何被安全有效地释放。

---
## 0、一句话总结
Harness Engineering ：不改模型本身，而是为 AI智能体构建一套外部的运行环境、约束规则与监控体系，让它安全、稳定、可控地在企业中落地运行。

## 一、什么是 Harness？

Harness 是包裹在大模型外面的**执行与治理系统**。它不是模型本身，而是围绕模型设计的一整套环境：规则、约束、工具、反馈回路、状态管理……

Martin Fowler 用三个同心圆来描述：

```
┌───────────────────────────────────┐
│  用户 Harness（你自己搭的）         │  ← CLAUDE.md、自定义 linter、测试、文档
│  ┌─────────────────────────────┐  │
│  │  Agent Harness（工具内置的）  │  │  ← Claude Code / Codex 的系统提示、代码检索
│  │  ┌───────────────────────┐  │  │
│  │  │  Model（模型本身）      │  │  │  ← Claude、GPT 等大模型
│  │  └───────────────────────┘  │  │
│  └─────────────────────────────┘  │
└───────────────────────────────────┘
```

- **内圈（Model）**：大模型本身，提供推理和生成能力
- **中圈（Agent Harness）**：工具厂商内置的系统提示、代码检索机制、编排逻辑
- **外圈（User Harness）**：用户根据自己的项目和环境搭建的规则、工具、反馈系统

> 一个设计良好的外层 Harness 要实现两个目标：
> 1. **提高首次就做对的概率**（预防问题）
> 2. **提供自纠反馈回路**，在问题到达人类之前自动修复

**不存在"标准 Harness 架构"。**

你要做的是根据你的具体场景回答三个问题： 1.

- 怎么让模型知道该干什么？

→ 规则/指令（prompt、配置文件、few-shot 示例） 2.

- 怎么让模型能干什么、不能干什么？

→ 工具边界（能调什么 API、能读写什么文件） 3.

- 怎么确保模型干对了？

→ 验证流程（自动测试、人工审核、多模型交叉验证）

## 二、两大核心机制：前馈与反馈

Martin Fowler 借用控制论框架，将 Harness 分为两个方向：

### Guides（引导 / 前馈控制）

在 agent 行动**之前**预防问题，提高首次做对的概率。

| 类型                 | 例子                                       |
| ------------------ | ---------------------------------------- |
| 推理型（Inferential）   | `AGENTS.md`、`CLAUDE.md`、Skills、架构文档、编码规范 |
| 计算型（Computational） | Language Server、CLI 脚本、codemods、项目模板     |

### Sensors（感知 / 反馈控制）

在 agent 行动**之后**发现问题，帮助它自纠。

| 类型  | 例子                                      |
| --- | --------------------------------------- |
| 计算型 | Linter、类型检查、结构测试（ArchUnit）、覆盖率检测        |
| 推理型 | AI Code Review、"LLM as Judge"、评估器 agent |

### 两者必须结合

| 只有 Guides | 只有 Sensors | 两者结合 |
|---|---|---|
| 编码规则写了，但不知道是否有效 | 每次犯同样的错再纠正，浪费 token | 越用越好，形成进化闭环 |
| Agent 的输出可能偏离规则而不自知 | Agent 从不学习，反复踩同一个坑 | 问题被修复后编码进 Guides，永久生效 |

**一个精妙的设计：** 自定义 Linter 的错误信息中注入修复指令。Agent 犯错时，Lint 不仅报错，还直接告诉它怎么改——这等于把 Code Review 自动化了。

## 三、计算型 vs 推理型

| 维度 | 计算型（Computational） | 推理型（Inferential） |
|---|---|---|
| 执行方式 | CPU 运行，确定性 | GPU/NPU 运行，语义分析 |
| 速度 | 毫秒到秒级 | 秒到分钟级 |
| 成本 | 便宜 | 昂贵（消耗 token） |
| 可靠性 | 高（确定性结果） | 中（存在非确定性） |
| 适用场景 | 代码风格、类型检查、结构测试、覆盖率 | 代码语义审查、架构评审、"LLM as Judge" |

**原则：** 能用计算型解决的，就不要用推理型。把推理型留给需要语义判断的场景。

## 四、三大治理维度

Harness 治理的目标不是单一的，可以按维度拆分：

### 1. 可维护性 Harness（Maintainability）

**目标：** 代码质量、风格一致性、架构边界、测试覆盖

这是目前**最成熟**的维度——大量现成工具可用（linter、formatter、测试框架）。

计算型 Sensor 能可靠地捕获结构性问题：重复代码、圈复杂度、缺失测试覆盖、架构漂移、风格违规。

推理型 Sensor 能部分处理需要语义判断的问题：语义重复代码、冗余测试、暴力修复、过度工程。但代价昂贵且不确定。

**两者都难以可靠捕获的高影响问题：** 问题误诊、不必要的功能、被误解的指令。这些仍需人类监督。

### 2. 架构适应度 Harness（Architecture Fitness）

**目标：** 性能要求、可观测性标准、模块边界

使用 Fitness Function 来定义和检查架构特征：

- 描述性能要求的 Skill（前馈） + 性能测试（反馈）
- 描述日志标准的 Skill（前馈） + 调试时对日志质量的反思（反馈）

### 3. 行为 Harness（Behaviour）

**目标：** 功能是否正确、用户需求是否被满足

这是**最大的未解难题**。当前大多数团队的做法：

- **前馈：** 功能规格（从简短提示到多文件描述）
- **反馈：** AI 生成的测试套件 + 人工测试

问题在于：这把太多信任放在了 AI 生成的测试上，而测试质量本身不可靠。

> "行为 Harness 是房间里的大象——我们仍然需要大量工作来找到好的 Harness，让我们有足够信心减少监督和手动测试。"

## 五、时机：质量左移

将检查尽可能前移，越早发现问题，修复成本越低：

```
代码生成前        代码生成后（自纠循环）    提交后（人工审查）    集成后（Pipeline）
─────────────────────────────────────────────────────────────────────────
AGENTS.md        /code-review             人类 Review          /architecture-review
架构文档          eslint                   手动测试             /detailed-review
/how-to-test     semgrep                                       变异测试
项目模板          覆盖率检测                                     全面回归测试
MCP Server
```

**原则：**
- 快速且便宜的检查 → 每次提交都跑（linter、快速测试、基础 code review）
- 昂贵的检查 → 只在集成后跑（变异测试、全量 code review、架构审查）

### 持续漂移检测

除了变更生命周期内的检查，还需要**持续运行**的 Sensor：

- **代码库漂移检测：** 死代码扫描、测试覆盖率质量分析、依赖扫描
- **运行时反馈：** SLO 退化监控、AI 采样响应质量、日志异常标记

## 六、可驾驭性（Harnessability）

不是所有代码库都同样容易被 Harness：

| 容易 Harness             | 难以 Harness         |
| ---------------------- | ------------------ |
| 强类型语言（TypeScript、Java） | 弱类型 / 动态类型（大量 any） |
| 清晰的模块边界                | 模糊的耦合关系            |
| 成熟的框架（约定大于配置）          | 大量自定义实现            |
| 绿地项目（从零开始）             | 遗留系统（技术债累积）        |

> "Harness 最被需要的地方，恰恰是最难构建的地方。"

技术选型本身就决定了未来的 Harness 上限。绿地团队可以从第一天就植入 Harnessability；遗留团队面临更艰难的处境。

---

## 七、Harness 模板（未来方向）

大多数企业有几种常见的服务拓扑：CRUD 业务服务、事件处理服务、数据看板……

未来，这些拓扑可能演化为 **Harness 模板**——一套针对特定结构和技术的 Guides + Sensors 包：

```
数据看板（Node）    → 对应的 Guides + Sensors
CRUD 服务（JVM）   → 对应的 Guides + Sensors
事件处理器（Go）    → 对应的 Guides + Sensors
```

团队选择技术栈时，可能会考虑"哪种技术已有成熟的 Harness 模板可用"。

---

## 八、人类的角色

人类开发者带来了**隐式 Harness**：

- 吸收的惯例和最佳实践
- 对复杂度的认知痛苦
- 对"我们这里不这么做"的直觉
- 组织记忆——知道哪条惯例是关键的，哪条只是习惯

**Agent 没有这些：** 没有社会问责，不会对 300 行的函数感到厌恶，不知道团队正在追求什么目标。

Harness 的本质是**将人类经验外显化和明确化**。但它只能做到一定程度。

> 一个好的 Harness 不应该追求完全消除人类输入，而是**将人类输入引导到最重要的地方**。

## 九、进化的全景

```
2023    Prompt Engineering（提示词工程）
          ↓ 人人学写 prompt
2024    Context Engineering（上下文工程）
          ↓ 发现 prompt 不够，需要管理系统上下文
2025-26 Harness Engineering（驾驭工程）
          ↓ 发现上下文也不够，需要设计整个执行环境
```

### 各家实践对比

| 公司/团队         | Harness 核心做法                                          |
| ------------- | ----------------------------------------------------- |
| **Anthropic** | GAN 式多 agent 对抗：生成器 + 评估器循环迭代                         |
| **OpenAI**    | 仓库环境设计：自定义 linter + 结构测试 + 垃圾回收式技术债管理                 |
| **Stripe**    | pre-push hooks + blueprints（将反馈 Sensor 集成进 agent 工作流） |
| **个人开发者**     | CLAUDE.md + pre-commit hooks + MCP servers            |

## 十、开放问题

Martin Fowler 指出了仍然待解决的关键问题：

1. **行为 Harness**——如何可靠验证功能正确性？
2. **一致性**——随着 Harness 增长，Guides 和 Sensors 如何保持同步、不互相矛盾？
3. **权衡判断**——当指令和反馈信号指向不同方向时，agent 能否做出合理取舍？
4. **覆盖率度量**——如果 Sensor 从未触发，是质量高还是检测不够？需要类似代码覆盖率的 Harness 覆盖率指标。
5. **工具整合**——前馈和反馈控制目前散布在交付各环节，需要统一配置和管理的工具。
